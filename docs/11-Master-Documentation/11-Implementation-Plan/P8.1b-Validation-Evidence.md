# P8.1b — Controlled POI Detail / Provenance API Extension

## Audit

- Endpoint: `POST /api/v1/routes/discover`.
- Result type: `RouteDiscoveryResponse.Result` from `RouteDiscoveryResult` and
  `RankedRoutePoiCandidate`.
- Persistence: `JdbcRoutePoiCandidateQuery` reads P3 POIs and categories; existing
  P3 schema already stores description and `geo.poi_provenance`.
- Domain: `PointOfInterest` and `SourceReference` remain authoritative persistence
  models. Discovery uses a small `ProvenanceSummary` projection.
- Provenance relation: one POI may have zero or many records. The existing repository
  order is `source_system, logical_key`; the discovery query selects the first record in
  that deterministic order with one bounded lateral query, avoiding N+1.
- Mobile DTO: `DiscoveryPoi`; optional fields are accepted by its existing response
  mapper but are not rendered by Preview or any P8.2 UI.

## Response contract

Existing fields remain unchanged: id, name, category, location,
distanceToRouteMeters, routeProgress, score and reasonCodes. The additive nullable
fields are `description`, `sourceLabel`, `sourceUrl` and `attribution`.

`description` is the factual persisted POI description, with null when absent. The
source label is the real `source_system`; URL and attribution are passed through only
when present. Internal logical keys, incorporation method, license, source record IDs,
retrievedAt, updatedAt and score metadata are never exposed. Freshness remains deferred.

## Compatibility and validation

- Request shape, routing, ranking, corridor and limit semantics are unchanged.
- POIs without description or provenance remain valid responses with null optional fields.
- Existing mobile payloads continue to deserialize; optional fields default to null.
- OpenAPI documents exactly the four nullable response fields and no freshness fields.
