# P8.3 — Backend-backed Discovery Category Filters

## Audit and decisions

- Discovery trigger remains `_calculateRoute`; the route is planned once, then the
  existing `DiscoverRoute` repository call is reused.
- `DioRouteDiscoveryRepository` now sends `categories` in the existing request; the
  controller retains origin/destination and applied codes for the current route session.
- “Todas” sends all ten authorized Discovery P3 codes explicitly because an absent or
  empty category list would otherwise allow Travel Service/ambiguous categories.
- Draft filter selection lives only in `DiscoveryFilterSheet`; results change only on
  Apply. Cancel leaves the applied request untouched. Restablecer selects Todas and
  Apply performs the corresponding backend requery.
- Backend remains authority for corridor, candidate selection, ranking and limit. Mobile
  does not rerank or locally filter results.

## UI and continuity

The filter sheet displays only the ten Discovery categories, supports multi-select,
accessible checkbox state, Cancel, Restablecer and Apply. The map summary shows Todas,
0 categorías or an active category count. Requery replaces markers without recalculating
the route. Empty filtered results use route-scoped language: “No encontramos lugares de
estas categorías para esta ruta.” Failed requery preserves the previous successful
results, route and applied context while showing the existing error status.

P8.1 Preview and P8.2 Detail continue to use the same POI model and applied filter
session; no Map/List implementation was added.
